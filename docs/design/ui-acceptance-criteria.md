## 0. 判定规则与取证工具

### 0.1 三级流程

| 阶段 | 时机 | 执行者 | 动作 | 不通过后果 |
| --- | --- | --- | --- | --- |
| **A 静态取证** | 每次提交，无需运行应用 | 工程师自检 / CI | 跑 §0.3 的 7 条只读命令，逐条勾 §1 门禁项 | 阻断合并 |
| **B 视觉取证** | 每轮 UI 合入后 | UI 验收设计师 | 按 §0.4 采集 5 张固定截图，填 §3 评分卡 | 总分 < 85 或任一维 < 80 → 需整改 |
| **C 外壳专项** | 无边框改造完成后、发版前 | QA + 工程师双签 | 执行 §6 的 18 项实机用例 | 任一 P0 失败 → 不可发布 |

### 0.2 主观话术 → 可计算口径

| 主观表述 | 本标准的判定口径 |
| --- | --- |
| 「颜色不统一」 | 非 `tokens.css` 文件中出现色值字面量（`#rgb`/`rgb()`/`hsl()`），**基线实测 18 处** |
| 「标题栏跟主界面不是一套」 | 标题栏取的令牌 ≠ `--bg-rail`，或标题栏新起一套按钮/菜单样式（须复用 `.btn` / `.menu`） |
| 「层次乱」 | `box-shadow` 取值不在 `{--shadow-1/2/3, --shadow-inset, --ring, --ring-danger, none}` 内；或标题栏出现任何投影 |
| 「尺度乱」 | `padding/gap/margin` 出现 4/8 梯度外取值（**基线 23 处**）或组件高度档数 > 5 |
| 「图标乱」 | 主展示区出现 emoji；同一容器内图标尺寸不同档；粗描系数（描边px ÷ 显示尺寸）不在 [7%,12%] |
| 「字重乱」 | 实际使用字重等级 > 4；基线实测仅 3 个取值（`inherit` / `--fw-medium` / `--fw-semibold`），**此项已达标，属守门项** |
| 「状态不全」 | 任一可点击元素缺 hover / active / disabled / focus 表现之一（含 `base.css:125` 全局焦点环继承） |
| 「动效乱」 | `transition/animation` 的时长或缓动写成字面量而非 `--dur-*` / `--ease*` |
| 「不符合 Fluent」 | 命中 §1.5 FL 系列任一门禁项，或命中 §2 反模式清单 |

## 1. 一致性判据（逐条可打勾）

> 记号：**[门禁]** 不通过即不可发布；**[整改]** 记入整改清单，可与发布解耦。
> 每条格式：检查什么 → 怎么取证 → 通过标准 → 常见失败形态。
> **五维归属**：C=色彩令牌化 / T=层次与层级 / S=尺度梯度 / I=图标与字体 / M=交互态与动效 / FL=Fluent 专项（FL 项按内容归属到对应维度计分，见 §3.1）。

### 1.1 色彩令牌化（维度 D1 = C 组 + FL1/FL2）

#### C1-1 [门禁] 令牌单一来源：非令牌文件零色值字面量

- **检查什么**：标题栏、应用内菜单、内容区用到的每一个颜色是否都来自 `tokens.css` 的 `--*` 变量。
- **怎么取证**：命令 **E1**。**基线实测 18 行**，分四簇：
  - 品牌紫 `#7c5cff` ×3（`base.css:265`、`layout.css:50`、`components.css:1431`）
  - 白色前景字面量 `#fff` ×6（`components.css:76,82,481,482,556,795`、`layout.css:49,192`、`views.css:434`）
  - 渐变亮端 `#86b2ff`（`components.css:49`）、`#ff8186`（`components.css:86`）
  - `stopping` 三件套 `rgba(176,124,240,…)`/`#c9a6ff`（`components.css:231-233`）+ 启动环 `rgba(255,255,255,.9)`（`base.css:276`）
- **通过标准**：E1 输出 **0 行**。
  **唯一豁免（须逐条在代码注释中登记）**：`var(--x, <字面量>)` 形式的组件私有变量缺省值，且该变量运行时由 JS 赋值——即 `--card-accent`（`views/instances.ts:349`、`views/wizard.ts:144`）与 `--avatar-bg`（`views/parts.ts:90`）。
- **常见失败形态**：为「调好看一点」直接在 `components.css` 写 `background: #1c2740`；新建 `chrome.css` 时写 `#7c5cff` / `#fff` / `rgba(255,255,255,.05)`。

#### C1-2 [门禁] 同一语义角色只用同一个令牌

- **检查什么**：外壳层与内容层对「应用底 / 面板底 / 抬升底 / 悬浮底 / 内嵌底」的取用是否一致。

  | 语义角色 | 唯一允许令牌 | 现有正确用点 |
  | --- | --- | --- |
  | 应用底 / 主工作区 | `--bg-app` | `.shell` `layout.css:11`、`.main` `layout.css:278`、`.view__tabs` `layout.css:340` |
  | 侧栏 / **标题栏** / 抽屉外框 | `--bg-rail` | `.topbar` `layout.css:22`、`.rail` `layout.css:104`、`.drawer` `layout.css:380` |
  | 卡片 / 面板 | `--bg-surface` | `.card` `components.css:659` |
  | 次级面板 / 控件底 | `--bg-surface-2` | `.btn` `components.css:18`、`.card__foot` `components.css:713` |
  | 悬浮层（菜单 / 模态 / Toast） | `--bg-elevated` | `.menu` `components.css:1227`、`.modal` `components.css:944`、`.toast` `components.css:1063` |
  | 内嵌底（输入 / 日志 / 代码） | `--bg-inset` | `.input/.textarea/.select` `components.css:336`、`.segmented` `components.css:586`、`.chip` `components.css:261` |

- **通过标准**：标题栏取 `--bg-rail` 或方案明确指定的另一角色；应用内菜单取 `--bg-elevated`；不存在「标题栏系统灰 + 内容区深蓝」的跨体系组合。
- **附带守门项**：`tokens.css:17` 的 `--accent-contrast` 与 `:74` 的 `--text-on-accent` 取值完全相同、语义重叠且前者**全域无使用点**（E1 取证 `text-on-accent|accent-contrast` 仅有 1 处引用），属重复令牌，须二选一删除。
- **常见失败形态**：自绘标题栏用「浅一点的灰」`#1f1f1f`；应用内菜单与内容卡片同档底色，菜单失去悬浮感。

#### C1-3 [门禁] 主进程色值与令牌同源，且随主题同步

- **检查什么**：主进程里的一切颜色（窗口底色、闪烁兜底页）是否与令牌一致；主题切换时是否同步。
- **怎么取证**：命令 **E6**；再切浅色 → 最小化 → 还原，观察首帧。
- **通过标准**：
  1. `BrowserWindow.backgroundColor` 等于 `--bg-app`。**闪现白帧或暗帧都算失败**。
  2. 渲染层切主题后，主进程 `backgroundColor` 同步更新。
  3. 兜底页（`src/main/index.ts:236` `placeholderPage()`，内联样式 `:240-244`）颜色同源。
- **现状取证（初审）**：`src/main/index.ts:31` `BACKGROUND_COLOR = '#0f1116'` ≠ `tokens.css:52` `--bg-app: #090d13`；兜底页另用 `#e6e8ee` / `#9aa3b2` / `#1b1f2a`；且 E6 全仓检索 `nativeTheme|setBackgroundColor` **零命中**，渲染层 `Theme` 变更（`renderer/data/store.ts:148,209`）无任何通道通知主进程——**主题切换后窗口底色必然滞留在启动时那一档**。
- **常见失败形态**：浅色主题下窗口底色仍是深色，还原窗口时闪深色帧。

#### C1-5 [整改] 强调色主题适配

- **检查什么**：用户可配的实例强调色（`--card-accent` / `--avatar-bg`）在浅色主题下是否仍可见。
- **怎么取证**：浅色主题打开 `#/instances`；命中 `views/instances.ts:349`、`views/parts.ts:90`；对 8 个预设色（`renderer/util/color.ts:6-15`）逐个计算对 `#ffffff` 的对比度。
- **通过标准**：卡片顶部 3px 色条（`.inst-card::before` `components.css:742-749`）对白底 ≥ 3:1，或在浅色主题下强制加 1px 描边 / 降低明度。
- **常见失败形态**：只在深色下验过色条。

### 1.2 层次与层级（维度 D2 = T 组 + FL2）

#### T2-1 [门禁] 阴影档位与组件高度成体系

- **检查什么**：每个浮起/浮出的层是否落在唯一一档阴影上。
- **怎么取证**：检索 `box-shadow:`，对照下表。**基线实测 28 处声明，取值 100% 命中下表**（无表外阴影）——本项是既有良好实践，作为回归守门项。

  | 阴影档 | 语义 | 允许的组件 |
  | --- | --- | --- |
  | `--shadow-1` | 静止平面上的卡片 | 卡片、实例卡片、主按钮、品牌标 |
  | `--shadow-2` | 悬停抬起 / 中等浮层 | 卡片 hover、`logview__jump`、窄屏浮层抽屉 |
  | `--shadow-3` | 最高浮层 | **仅**模态、菜单、Toast、窄屏浮层抽屉 |
  | `--shadow-inset` | 内凹高光 | 头像、内嵌块 |
  | `--ring` / `--ring-danger` | 焦点环 | 输入框、开关、卡片 |

- **通过标准**：映射 100% 命中；**自绘标题栏不得出现任何投影**（靠 1px 下沿 + 底色差表达边界）。
- **常见失败形态**：标题栏为「显得立体」加投影；菜单用 `--shadow-2` 与卡片同级。

#### T2-2 [门禁] 分隔线成体系，外壳与内容同源

- **检查什么**：结构性分隔线是否只取三档描边之一。
- **怎么取证**：检索 `border-*: .*solid|dashed`；在 S1 上比对标题栏下沿、视图头下沿、卡片头下沿三条线的颜色与粗细。
- **通过标准**：
  - 结构性分隔（标题栏下沿、侧栏右沿、抽屉左沿、视图头下沿）统一 `1px solid var(--border-subtle)`。**基线实测已 100% 达标**（`layout.css:23,105,229,295,339,387,405`、`components.css:671,712,1045,1298,1511,1633,1669`、`views.css:114,357`），属守门项。
  - **卡内底部分隔线型必须二选一**：`.card__foot`（`components.css:712`，`solid`）与 `.engine-card__foot`（`views.css:269`，`dashed`）当前一处实线一处虚线，同一屏 `#/engines` 内可同时看到两种线型。
  - 「语义色左标记」粗度必须统一：`.toast` 为 **3px**（`components.css:1065`），而 `.logline` 声明 `border-left: 2px solid transparent`（`components.css:1534`，各语义色变体只改颜色不改宽度）。
- **常见失败形态**：自绘标题栏用 2px 实线「强调」；标题栏下沿写死 `rgba(255,255,255,.14)` 变成比内容区更亮的一条。

#### T2-3 [门禁] 层级序不倒挂

- **检查什么**：`z-index` 是否只来自 `--z-*`，且值序为 `rail(10) < topbar(20) < drawer(30) < menu(60) < modal(80) < toast(100)`。
- **怎么取证**：`Select-String -Path src\renderer\styles\*.css -Pattern 'z-index'`。
- **通过标准**：检索结果**全部为 `var(--z-*)`**（基线实测 8 处，无一硬编码，属守门项）；浮层叠压关系符合值序。

### 1.4 图标与字体（维度 D4 = I 组 + FL3）

#### I4-1 [门禁] 主展示区禁止 emoji 与 SVG 混用

- **检查什么**：界面主展示区（标题栏、侧栏、按钮、菜单、页签、空态）是否出现 emoji 字符。

  - **状态点须为图形而非字符**：`shell.ts:266` 用文本字符 `●` + 内联 `fontSize: '15px'`（梯度外字号）表达实例状态，应改为 `h('span', { class: 'state-dot' })` + CSS（`width/height` + `border-radius: var(--r-full)` + 状态色令牌）。

#### I4-2 [门禁] 图标尺寸分档一致

- 见 **S3-5**。补充量测口径：**同一容器内**（`.view__actions`、`.topbar__actions`、`.menu`、`.toolbar`、`.drawer__head`）所有图标的 size 必须同档；跨档只允许「容器级差异」（空态 24 vs 行内 16）。
- **常见失败形态**：同一行「运行日志」按钮 16px、主题切换按钮 15px、新建按钮 15px。

#### I4-3 [门禁] 描边权重与尺寸成正比（**本条判据已按实测修正**）

- **检查什么**：`icons.ts:97` 固定 `stroke-width="1.8"`、`viewBox="0 0 24 24"`（`icons.ts:92`），因此**视觉描边恒为 1.8px**，与显示尺寸无关。图标越小，1.8px 占的比重越大。
- **判定口径（可计算）**：**粗描系数 = 描边px ÷ 显示尺寸**，必须落在 **[7%, 12%]**。
  - 12px → 1.8/12 = **15.0%** ❌ 明显偏粗
  - 14px → 12.9% ❌ 偏粗
  - 16px → 11.3% ✅
  - 18px → 10.0% ✅
  - 19px → 9.5% ✅
  - 24px → 7.5% ✅
- **通过标准**：全部图标落在 [7%, 12%]；实现方式为按显示尺寸分档设置 `stroke-width`（建议：`size ≤ 12 → 1.4`；`13–15 → 1.6`；`16–21 → 1.8`；`≥ 22 → 2.0`），并同时把 E5 的 10 档收敛到 S3-5 的 6 档。
- **常见失败形态**：11–12px 图标看起来像实心块；同一行 12px 与 18px 图标视觉重量差近一倍。

#### I4-4 [整改] 线性与填充风格不混用

- **检查什么**：`icons.ts` 中 `fill="currentColor" stroke="none"` 的图标与描边图标的并置。**实测 3 个实心图标**：`play`（`icons.ts:14`）、`stop`（`icons.ts:15`）、`more`（`icons.ts:67` 三个 1.5r 圆点）。
- **怎么取证**：`Select-String -Path src\renderer\icons.ts -Pattern 'fill="currentColor"'` + 目视 S1。
- **通过标准**：同一容器内不得混用。若「播放/停止」因可识别性必须实心，须在**整个动作条**内统一规则并登记例外清单（`views/instances.ts:398` 的 `power` 描边 13px 与 `:407` 的 `play` 实心 13px 同排并列，即现存反例）。
- **常见失败形态**：实心图标在 13px 下视觉重量明显重于描边图标，同一行看起来「有的大有的小」。

#### I4-5 [门禁] 字体栈符合 Windows 11（FL3）

- **检查什么**：`--font-ui` 是否把 Segoe UI Variable 置于优先位置。
- **怎么取证**：`Select-String -Path src\renderer\styles\tokens.css -Pattern 'font-ui'`。
- **通过标准**：`--font-ui` 优先序为 `"Segoe UI Variable Text" → "Segoe UI Variable Display" → "Segoe UI" → 中文回退（"Microsoft YaHei UI" 等） → system-ui`。理由：Win11 Fluent 的排版基准是 Segoe UI Variable；当前 `tokens.css:77-78` 以 `"Microsoft YaHei UI"` 打头，**西文与数字会全部落在中文字体上**，字形与字重轴都与 Win11 原生界面不同——这是「不符合 Win11 Fluent」最容易被一眼看出的点。
- **常见失败形态**：为中文显示稳定而把中文字体放最前，导致 `WhalesLauncher`、`v1.0.0`、`F:\` 等西文/路径字形与系统界面不一致。

#### I4-6 [门禁] 字号只来自 `--fs-*` 梯度

- **检查什么**：`font-size` 取值。白名单：`--fs-xs(11) / --fs-sm(12) / --fs-md(13) / --fs-lg(15) / --fs-xl(18) / --fs-2xl(22) / --fs-3xl(28)`。
- **怎么取证**：E2 的 `font-size` 分支。**基线实测 7 处字面量**：`base.css:19`（根字号 16px，**豁免**）、`components.css:793/804/811`（头像 emoji 22/16/28px，**用户内容通道，登记豁免**）、`layout.css:190`（左栏头像 emoji 16px，同上）、`views.css:471`（`.emoji-btn` 19px，同上）、`views.css:653`（进度步骤序号 10px，**应整改**为 `--fs-xs` 或改为图形标记）、`shell.ts:266`（状态点 15px 内联，**应整改**，见 I4-1）。
- **通过标准**：与令牌无关的字面量 ≤ 2 处，且均为已登记的图形化字符。
- **常见失败形态**：14px 这个「看起来更舒服」的值混进标题栏（梯度里没有 14）；同一层级两个标签一个 12px 一个 13px。

#### I4-7 [门禁] 字重层级 ≤ 4 级且与角色一一对应

- **检查什么**：`font-weight` 的取值集合与用途。
- **怎么取证**：`Select-String -Path src\renderer\styles\*.css -Pattern 'font-weight\s*:'`。
- **现状取证（初审）**：全域仅 3 个取值——`inherit`（`base.css:41`）、`var(--fw-medium)` ×11、`var(--fw-semibold)` ×17。**等级数达标（≤4），但 `--fw-regular`(400) 与 `--fw-bold`(700) 定义后全域无使用点，属死令牌**（正文字重靠浏览器默认 400 承担，未走令牌）。
- **通过标准**：
  1. 不出现 `font-weight: 550` 或 `font-weight: bold` 这类梯度外值。
  2. 语义角色绑定唯一字重：正文/菜单项/页签 400；次级强调/按钮/卡片小标题 500；区域标题/视图标题/弹窗标题/品牌名 600。
  3. 死令牌二选一：删除，或在设计文档中明确唯一允许用法并给出使用点。
  4. **选中态不得靠字重变化表达**：`.tabs__item.is-active`（`components.css:910`）加 500 而 `.rail__nav-btn.is-active`（`layout.css:258`）不加，须二选一统一——否则切换时文字宽度跳动。
- **常见失败形态**：标题栏 600、卡片标题 600、菜单组标题却用 700，出现第 5 级。

#### I4-8 [整改] 行高梯度与等宽字体分工

- **行高**：允许 `--lh-tight(1.3) / --lh-normal(1.55)`，或图形化场景的 `1`。**现存孤值 5 处**：`components.css:347`（textarea 1.6）、`:1537`（logline 1.6）、`:1666`/`:1684`（YAML 1.65）、`views.css:291`（console 1.6）。整改方式：新增 `--lh-code: 1.6` 令牌并 5 处统一引用。
- **等宽字体分工**：`--font-mono` 只允许用于机器可读文本（路径、ID、版本号、日志、YAML、快捷键提示、字节数），禁止用于中文界面文案。**现存疑点**：`.chip`（`components.css:254-268`）会承载中文标签（如 `shell.ts:52` 的「演示数据」），应拆为 `.chip`（UI 字体）与 `.chip--mono`。
- **常见失败形态**：日志区 1.6 而设置页文本域 1.55，两块并排时行距不齐。

#### I4-9 [门禁] 圆角体系符合 Fluent 几何（FL-1）

- **检查什么**：圆角档位是否服务于 Fluent 的「小控件 4px / 表面 8px / 浮层 12px」逻辑，且不存在无理由的档位。
- **怎么取证**：统计 `border-radius` 令牌使用分布 + 对照下表。
- **通过标准**：

  | 我的方案（本文件裁决） | Fluent 原生参照 | 判定 |

  | 交互控件（按钮/输入/菜单项）用 `--r-sm(6)` 或 `--r-md(8)` | Control corner 4px；表面 8px | **允许**，但**同一类控件必须同档** |

### 1.5 交互态与动效（维度 D5 = M 组 + FL4）

#### M5-1 [门禁] 四态全覆盖（hover / active / disabled / focus）

- **口径**：判定「可点击」的范围 = `<button>`、`<a>`、`[role=menuitem]`、`[role=tab]`、`<label class="checkbox|switch">`、`<select>`、`<input>`。
- **焦点态的正确取证方式（关键）**：`base.css:125-129` 存在**全局** `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }`，因此**凡是没有显式 `outline: none` 的可聚焦元素，键盘焦点环自动成立**——此时「文件里没有 `:focus-visible` 规则」**不是缺陷**，不得据此判失败。
- **通过标准**：
  1. 每个可点击元素要么继承全局焦点环，要么有显式 `box-shadow: var(--ring)` / 内缩 outline；**不存在既 `outline: none` 又无替代的节点**。
  2. hover / active / disabled 三态在**同类元素间一致**。
- **现状缺口（证据已逐条复核）**：

  | 元素 | 现状 | 判定 |
  | --- | --- | --- |
  | `.menu__item` | `components.css:1234-1261`：hover ✅ / disabled ✅ / **active ❌** / 焦点靠全局继承 ✅ | **须补 `:active { background: var(--bg-active) }`** |
  | `.emoji-btn` / `.swatch` / `.color-input` / `.search__clear` / `.toast__close` / `.copy-btn` / `.logview__jump` / `.steps__item` | 均有 hover/active（`views.css:479,485,512,516`、`components.css:357-361`、`:1144`、`:1766,1771`、`:1601`），焦点靠全局继承 | **判定为通过**（与直读 CSS 文本的初判不同，此处以「全局环 + `outline:none` 检索」为准） |
  | `.btn` | hover ✅（`components.css:28`）/ active ✅（`:33` `translateY(1px)`）/ disabled ✅（`:37` `opacity:.45`） | 通过 |
  | 窗口控制按钮（新增） | — | 必须在 §6 逐项实测 |

- **常见失败形态**：Tab 键能聚焦但看不到焦点环；`outline: none` 后忘补 `box-shadow: var(--ring)`。

#### M5-2 [门禁] 焦点环统一，窗口控制按钮例外须内缩

- **通过标准**：
  1. 默认（容器层）：全局 `:focus-visible` = `outline: 2px solid var(--accent); outline-offset: 2px`（`base.css:125-129`）。
  2. 需要贴元素边缘时（**窗口控制按钮、贴窗口边缘的控件**）：`outline-offset` 必须为**负值**（如 `-2px`），否则环被窗口边缘裁切。
  3. 输入框/开关用 `box-shadow: var(--ring)`（`components.css:368`、`:560`），危险态用 `--ring-danger`（`:379`）。**只允许这三种写法**，禁止 `outline: 1px dashed …`、只改 `border-color` 不补环、`filter: drop-shadow`。
- **已知不一致须统一**：`.inst-card:focus-visible`（`components.css:762-766`，因卡片 `overflow: hidden` 改用 `box-shadow: var(--ring), var(--shadow-2)`）理由成立，须在代码注释标注为模式二的合法特例。
- **常见失败形态**：按钮上是外扩 2px 实线环，输入框上是外扩 3px 柔光环，窗口按钮上被裁掉一半。

#### M5-3 [门禁] 关闭/破坏性操作 hover 语义一致

- **通过标准**：

  | 场景 | 允许的 hover 表现 |
  | --- | --- |
  | **窗口关闭**（自绘标题栏） | 必须危险语义：`--danger` 底 + `--text-on-accent` 前景，active 用 `--danger-press` |
  | 模态/抽屉/Toast 的关闭 | 中性 `--bg-hover`（**不得**用危险色） |
  | 删除/停止等业务动作 | `--danger-soft` 底 + `--danger-text` 前景 |

- **层级校验**：窗口关闭按钮的危险反馈强度必须 **≥** 业务删除按钮，否则用户在标题栏会误关窗口。
- **对比度校验**：白图标 on `--danger #f2555a` = **3.37:1** ✅（非文本图形 3:1）；浅色 `--danger #dc3f45` = **4.34:1** ✅。
- **常见失败形态**：关闭按钮与最小化/最大化共用中性 hover，无法区分。

#### M5-4 [整改] 禁用态一致

- **通过标准**：禁用表现只用一种（建议 `.btn:disabled { opacity: .45 }`，`components.css:37`）；`.input/.textarea/.select:disabled`（`components.css:382-387`，`opacity:.5` + `cursor: not-allowed`）须与之一致；`cursor: not-allowed` 必须存在（`base.css:74-75` 已全局覆盖 `button:disabled`，`<select>`/`<input>` 需单独确认）。
- **常见失败形态**：有的禁用按钮变灰 45%，有的只改 cursor。

#### M5-5 [门禁] 时长只用 `--dur-1/2/3`，缓动只用 `--ease*`

- **怎么取证**：命令 **E3**。
- **通过标准**：`transition`/`animation` 的时长与缓动全部为 `var(--dur-*)` / `var(--ease*)`。**基线实测：40 条动效声明 100% 令牌化**（29 条 `transition` + 16 条 `animation`，其中 5 条为 `animation` 简写形式，故 40 条命中 `var(--dur`/`var(--ease`）——**本项是既有最佳实践，切勿在新代码里破坏**。
  **豁免（须 ≤ 4 处且不成倍数关系）**：无限循环动画周期可用字面量秒数，基线为 `.spinner` 0.7s（`components.css:161`）、`.boot__mark` 0.9s（`base.css:278`）、`.skeleton` 1.4s（`components.css:1457`）、`.badge__dot--pulse` 1.5s（`components.css:251`），另 `base.css:298,300` 的 `0.01ms !important` 属 reduced-motion 兜底（正确用法）。
- **映射规则**：`--dur-1(120ms)` = 状态反馈（hover/active/focus）；`--dur-2(160ms)` = 出现/位移；`--dur-3(220ms)` = 大区域尺寸变化。**新代码不得为「手感」自定义时长**。
- **Fluent 参考区间**：Win11 Fluent 的控件过渡集中在 100–250ms，本项目 120/160/220ms 落在区间内 ✅。
- **常见失败形态**：自绘标题栏按钮 80ms、应用内菜单 300ms、内容按钮 120ms，同一次操作里三种节奏。

#### M5-6 [门禁] `--ease-spring` 使用范围受限

- **通过标准**：仅 `--ease` / `--ease-in-out` / `--ease-spring` / `linear`（限循环旋转与流光）。`--ease-spring` 仅允许尺寸/位移的弹性收尾（现有正确用点：`.checkbox input::after` `components.css:477-486`、`.switch__track::after` `:537-547`），**禁止**用于 hover 变色，**禁止**用于窗口控制按钮等系统 chrome（应使用 `--ease`）。
- **常见失败形态**：菜单用 `ease-out`、模态用 `ease`、Toast 用 `linear`。

#### M5-7 [整改] 出入场时长成对

- **通过标准**：退场时长 ∈ [入场时长 × 0.6, 入场时长 × 1.0]。
- **现状取证（初审）**：`.modal` 入场 `wl-rise var(--dur-2)`（`components.css:949`）vs `.is-closing` 退场 `var(--dur-1)`（`:964-970`）+ `modal.ts:81-83` 的 `setTimeout(…, 150)` **硬编码 150ms**（比 `--dur-1`=120ms 多 30ms，属魔法数）；`.toast` 进出均为 `--dur-2` ✅；抽屉开启 220ms（`layout.css:382`）而**关闭时 `shell.ts:277-285` 直接 `clear(drawer)` 清空内容**——过渡期间抽屉是空的，「滑入 220ms、空壳滑出」观感割裂。
- **常见失败形态**：抽屉滑入 220ms、滑出瞬清。

#### M5-8 [整改] `prefers-reduced-motion` 全局兜底

- **通过标准**：`base.css:294-303` 的全局降级规则必须保留且生效；新增动画不得用内联 `style` 或 `animation` 属性绕过。
- **取证**：Windows 设置 → 辅助功能 → 视觉效果 → 关闭动画效果，重启应用，确认无位移/旋转动画。
- **常见失败形态**：新增标题栏按钮动效用内联样式逃过 CSS 兜底。

#### M5-9 [门禁] 鼠标/键盘双通道与触达面积（FL-4）

- **通过标准**：
  1. 窗口控制按钮的三按钮**等宽等高**，顺序为 最小化 → 最大化/还原 → 关闭，`gap: 0`。
  2. 交互元素命中区 ≥ **32×32px**（窗口控制按钮应满高、宽 ≥ 46px，符合 Windows 习惯）。
  3. `:active` 反馈统一为 `translateY(1px)`（`components.css:34`、`:611`、`layout.css:170`），**不得用 `transform: scale()`**（会引起文字模糊且与现有约定冲突）。
  4. 禁用元素不得使用 `pointer-events: none` 之外的「假禁用」（如仅变浅仍可点击）。
- **常见失败形态**：三按钮宽度不等；用 `scale(0.96)` 做按下反馈。

## 2. 一致性反模式清单（命中即判定不一致/不符合 Fluent）

> **命中 P0 即整体不通过**，无论评分多少。

| 编号 | 反模式 | 严重级 | 判定理由 |
| --- | --- | --- | --- |
| **A-01** | 系统原生菜单栏与自绘菜单**同时可见**（`autoHideMenuBar: false` + `Menu.setApplicationMenu` 未删，同时标题栏下又有一排自绘菜单） | **P0** | 同一屏出现两套菜单，字体系/间距系/交互系完全不同；用户原话所指的「菜单栏与主界面不一致」正是此形态 |

### 6.1 必验用例（18 项）

### 6.6 外壳形态裁决表（A 全自绘 / B WCO，二选一，禁止混用）

> **这一节处理需求内部的一处真实张力**：用户原话要求「遵循 Windows 11 原生 Fluent」，而 Fluent 的原生表现之一是**窗口控制按钮交给系统**（WCO）；但 `ui-redesign.md` §2.5 经三方案对比后**否决了 WCO**，理由是 `titleBarOverlay.color` 会引入第二处色源（标题栏底 + overlay 底两套色）、`symbolColor` 只能给一种颜色因而无法实现 hover 变亮 / active 加深、且系统按钮固定 46×32 与 40px 标题栏高度不统一。
> **验收方的裁决**：**接受 A 方案（全自绘）**，但该接受是有条件的——自绘必须在**几何、状态、无障碍**三个维度上达到或超过系统按钮的可用性水平，并把偏离记入 §3.4。两条路径的判据如下，**无论走哪条，混用即 P0**。

| 判据 | A 形态：全自绘窗口按钮（**已采纳**，走 §6.1 W-01~W-18） | B 形态：WCO 系统绘制（走 §6.5 WC-01~WC-08） |
| --- | --- | --- |
| 几何 | 3 按钮**等宽等高**（建议 46×40 = 满高），`gap: 0`，顺序 最小化→最大化/还原→关闭；图标 16px，取自 `icons.ts` 同一 24 网格 | 由系统绘制，46×32；**必须**核对与标题栏高度的对齐关系（40px 标题栏会留 8px 空白） |
| 状态 | 关闭 hover 必须 `--danger` + `--text-on-accent`，active `--danger-press`；其余两键中性 `--bg-hover`/`--bg-active`；实现要求见 §1.5 M5-3 | 系统只有一种 `symbolColor`，**无法**表达 hover 变亮——必须在 §3.4 登记该能力损失 |

| Snap Layouts | **失去**（自绘按钮无法触发系统布局浮层）；缓解：`Win + Z` 仍可用 → **须登记**（§3.4 第 5 行） | 保留 |
| 判据汇总 | 允许，前提：§3.4 登记 Snap Layouts 损失 + W-02 图标同步由主进程事件驱动（禁轮询）+ W-15 关闭走 `win.close()` | 允许，前提：WC-02 色差为 0 + WC-03 对比度 ≥ 3:1 + §3.4 登记 hover/active 能力损失 |

**裁决执行要求（三条，缺一不可）**

1. **形态必须在提交说明中显式声明**（A 或 B），验收时按对应章节执行用例；未声明即视为形态不明，直接判 ❌。
2. **禁止混用**：自绘窗口按钮与 `titleBarOverlay` 同时存在 = P0（命中 §2 A-08 / WC-08）。
3. **A 形态必须把「失去 Snap Layouts」写入 §3.4 第 5 行**；B 形态必须把「无法做 hover/active」写入 §3.4 并新增一行。**未登记的偏离按 A-23 处理（P1）**。

## 9. 结语：这套标准如何拦截问题

这套标准的拦截力来自四个设计选择：**把主观判断换成可计算量**、**把外壳与内容的一致性设为一票否决**、**把取证固化到具体文件行号与可复制命令**、**把对 Fluent 的偏离变成必须登记的显式决策**。

具体来说：改动标题栏的工程师在提交前跑一遍 §0.3 的七条只读命令，自己就能看到 E1 从 18 行变成 21 行（新写了一个硬编码色）、E2 的间距孤值从 23 涨到 26、E5 的图标档位从 10 变成 11——**不需要评审会就能拦住一半问题**；接着 §1.1 的对比度表与 §1.6 FL5-2 的合成色表把「好看」拆成了具体数字，标题栏按钮的图标色、关闭按钮 hover 的红色、菜单面板的描边都必须在深浅两套主题下分别达标，杜绝了「深色下看着还行」这种单主题验收；§3.2 的 X 组则把最致命的情形钉死——**X3 只允许一个答案**（应用内菜单必须是同一个 `.menu` 组件），X1/X2/X4/X8 任意一项不通过直接判不可发布，于是「为标题栏另写一份 CSS」这条最常见的滑坡在流程上就不成立；§6 的 18 项实机用例覆盖 `-webkit-app-region` 分区声明、最大化图标同步、`Alt` 与快捷键冲突、关闭按钮绕过退出确认这四类改造特有的 P0 功能缺陷，保证「标题栏好看但点不动」「菜单做出来了但和右键菜单长得不一样」「系统菜单栏还残留着」这三种伪装成「已统一」的失败形态在发布前亮红灯；最后 §3.4 的 Fluent 偏离登记表把「本项目为什么是 12px 圆角、为什么不做 Mica」这类问题从口头讨论变成表格里的一行，使 Fluent 一致性既可验收又可维护——后续任何人新增控件，都只需回答「它属于哪一档令牌、有没有登记例外」两个问题。
